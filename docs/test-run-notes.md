## Найденные проблемы

(заполняется по ходу прогона; формат: Фаза / файл·строка / описание / насколько критично)

### P1. Ledger-учёт ломается культурой (ru-RU) — КРИТИЧНО [Фаза 0/4/10]
- **Файл:** `scripts/cleanup-common.ps1`, функция `Write-Ledger` (строка с `$row = ... -f ...`).
- **Симптом:** в `ledger.csv` строки содержат 9 полей при 8 колонках: `2026-08-18 19:35:08,baseline,volume C,C:,56698,23046875,0,baseline,0`. `size_before_mb=56698`, `size_after_mb=23046875`, `status=0`, `removed_mb=baseline` — все колонки съезжают, `Import-Csv`-свод Фазы 10 даст мусор, суммы по фазам неверны.
- **Причина:** PowerShell `-f` форматирует числа текущей культурой. В ru-RU десятичный разделитель — запятая: `56697.0703125` печатается как `56697,0703125`, т.е. одна CSV-ячейка разрывается на две («56698,23046875» — это на самом деле одно число 56698.23046875 МБ = 55.37 ГБ свободного места).
- **Фикс (применён в репо):** числа форматируются явно `([double]$N).ToString('0.####', [CultureInfo]::InvariantCulture)`. Проверено: `2026-08-18 19:41:44,baseline,volume C,C:,56696.9922,0,baseline,0` — 8 полей, статус/removed на местах.
- **Сопутствующая проверка:** парсинг `[double]'56696.9922'` и `Measure-Object -Sum` в ru-RU работает (PowerShell кастит числа инвариантно) — `ledger-report.ps1` в безопасности.
- **Оговорка:** риск касается любых `-f` с числами, которые потом машинно парсятся (CSV, сортировка по значению). TSV-отчёты (dirs_top.txt с `{0:N2}`) безопасны только пока читаются человеком — см. улучшение U1.

### P2. Массив из конкатенаций схлопывается в один элемент — КРИТИЧНО [Фаза 2]
- **Файл:** `scripts/inventory-quick.ps1:40` (`foreach ($d in @($env:USERPROFILE + '\Desktop', ...))`).
- **Симптом:** `installers.txt` **не создавался вообще** (молча), хотя на Desktop были `.exe`/`.rar`. `$d` в цикле оказывался одной строкой `C:\Users\планктон\Desktop C:\Users\планктон\Downloads ...` → `Test-Path` = False → 0 установщиков.
- **Причина:** в PowerShell **запятая связывает сильнее, чем `+`** (эмпирика в PS 5.1.19041: `4, 5 + 6` → `[4,5,6]`, `'a'+'b','c'+'d'` → строка `"ab cd"`). Элементы массива, построенные конкатенацией без скобок, склеиваются в одно выражение.
- **Фикс (применён):** каждый `+`-элемент в скобках: `@(($env:USERPROFILE + '\Desktop'), ($env:USERPROFILE + '\Downloads'), ...)`. Проверено: `installers.txt` теперь пишется (3 установщика).
- **Класс бага:** проверены все скрипты — других `+`-в-списке вне скобок нет (в `run-elevated.ps1:28` и `scan.ps1:97` скобки уже есть). Добавить в Pitfalls скилла: «элементы массивов со `+` — всегда в скобках».

### P3. Литеральный `` `t `` в одиночных кавычках — using-дубль известного питфолла [Фаза 2]
- **Файл:** `scripts/unused-detect.ps1:67`.
- **Симптом:** `unused_hints.txt` содержал `Cuphead`t5524 МБ`t...` — литеральный backtick+t вместо таба. Ровно тот питфолл «таб только в двойных кавычках», из-за которого когда-то ломались scan/Dupe — в `unused-detect.ps1` он остался.
- **Фикс (применён):** формат-строка переведена в двойные кавычки. Проверено: в файле теперь настоящий таб (`Cuphead<TAB>5524 МБ<TAB>...`).
- **Вывод:** пройтись по всем скриптам на `'...'`t...` — одиночные кавычки с backtick-t (статически всё ещё ищется через grep).

### P4. `installers.txt` не перезаписывается, когда установщиков больше нет — СРЕДНЕ [Фаза 2/4]
- **Файл:** `scripts/inventory-quick.ps1`, секция установщиков (в прогоне 2026-08-18).
- **Симптом:** после удаления B1–B3 (20:05) повторный `inventory-quick` продолжал показывать в `installers.txt` те же удалённые файлы со старыми размерами — Фаза 3/4 видела бы несуществующие установщики.
- **Причина:** `Set-Content` с пустым пайплайном **не перезаписывает/не трогает файл** — остаётся предыдущее содержимое (в отличие от создания пустого файла). Раздел установщиков писал только при непустом `$ins`.
- **Фикс (применён):** явная ветка — при пустом `$ins` писать маркер `(пусто — установщиков нет)`, по образцу scan.ps1. Проверено: `installers.txt` перезаписывается.
- **Вывод:** проверить остальные `Set-Content` от потенциально пустых коллекций (recyclebin/cache — ок, пишут всегда; installers был разрывом).

## Потенциальные улучшения

(заполняется по ходу прогона)

### U1. Единое инвариантное форматирование чисел в скриптах
Раз всё, что рано или поздно парсится (ledger, отчёты, сортировки), должно печатать числа с точкой — стоит ввести в `cleanup-common.ps1` хелпер (например `fmt-N <value> [decimals]` с invariant culture) и использовать его во всех CSV/TSV-выходах, а `-f` с культурой оставить только для человекочитаемого лога. Сейчас `dirs_top.txt`/`files_top.txt`/`cache_sizes.txt`/`installers.txt` печатают `{0:N2}` → в ru-RU будет «56 697,00»/«0,12» (NBSP+запятая); пока это читает человек — ок, но любая будущая сортировка/паттерн-матч по значению сломается.

### U2. Ворота дисков vs кэши на других томах
В `cache_sizes.txt` `%TEMP%` оказался на `D:\Temp\CodexUserTemp` — то есть Фаза 4 «мусор и кэши» по умолчанию соберёт цели вне выбранного диска (выбрали C:). Уточнить в скилле: либо кэши режутся по фактическому тому (и тогда ворота дисков должны это явно отражать), либо в отчёте помечать «вне выбранного диска — пропускаем/по желанию». В этом прогоне TEMP на D: не чистим (0,07 ГБ, несущественно).

### U3. Рабочая папка внутри git-репо: `git status`
Проверено: в репо **уже есть `.gitignore`** с `pc-cleanup-logs/` и `**/pc-cleanup-logs/` (плюс `*.log`, `*.tmp`) — журнал прогона не засоряет `git status`. Пара «docs/test-run-notes.md» появится как untracked — это by-design (артефакт теста). Убедиться, что в самом скилле (SKILL.md/фазы) упомянут случай «рабочая папка в репо — добавь в .gitignore», чтобы это не открывалось заново.

### U4. Steam-игры: в «неиспользуемые» как кандидаты не попадать, но объём — показывать
Cuphead (Steam, `D:\Games\Steam\steamapps\...`) попал в кандидаты «возможно не используется»: фильтр `skipRe` (строка 40) проверяет только `Name` (там `Steam ` с пробелом — ловит «Steam Client», но не путь), а по пути установки (`Loc`) не фильтрует. Итог: игра без надёжного следа запуска (Steam-игры не пишут MuiCache/UserAssist), помечена как будто её можно удалить напрямую — а удалять Steam-игру нужно только через Steam.
**Уточнение дизайна (важно):** из анализа объёмы Steam НЕ пропадают. Скилл не перестаёт *показывать*, где занято место; он просто не ставит Steam-игры и тяжёлые бинарники в блок «кандидат на удаление», а выносит их в **информационный блок «где место»**:
  - новый артефакт (например `steam_games.txt`): Steam-библиотеки → топ игр по размеру + appID + пометка «удаление через Steam» (юзер сам удаляет в клиенте); источник — `steamapps\libraryfolders.vdf` + `steamapps\common\*` (по всем машинам на дисках, а не по реестру Uninstall, где игр почти нет);
  - тяжёлые файлы/бинарники и так видны в `files_top.txt`/`dirs_top.txt` (топ-50) и в Фазе 3 — они остаются в отчёте как информация («здесь X ГБ: язык/длл/установщик»), но не как кандидаты, если это данные/компоненты.
**Принцип, который зафиксировать в скилле:** «показать где место — всегда; кандидатами на удаление — только то, что безопасно чистится одним движением» (report-then-approve: показать ≠ предложить удалить).
**Реализация (предлагаемая):** (1) в `unused-detect.ps1` — скип по `Loc` внутри библиотеки Steam (`\\Steam( Library)?\\steamapps\\|\\steamapps\\common\\`); (2) новый лёгкий скрипт `steam-games.ps1` → `steam_games.txt` для Фазы 3.

### U5. `run-elevated.ps1 -Args @(...)` не работает из git-bash
Синтаксис `-Args @('-Work','путь')` в командной строке, пришедшей из git-bash/Hermes, ломается: `@(` — это bash-синтаксис («syntax error near unexpected token (`). Из bash нужно `-Args '-Work' 'путь'` (слова раздельно) или параметр со значением по умолчанию. В скилле стоит оговорить вариант вызова из bash и/или сделать `$Work` в elevated-скриптах опциональным с дефолтом. (Косвенно: stdout elevated-скрипта не виден — «читай лог/ledger, не консоль» — подтвердилось вживую.)

### U6. Хевристика `LocExists=False` ловит Package Cache, а не сироты
Все 12 записей без папки — это `C:\ProgramData\Package Cache\{GUID}` / `AppData\Local\Package Cache\{GUID}` у VC++-рантаймов, .NET Desktop Runtime, Python, UE4-пререквизитов. Это установленные системные компоненты, их InstallLocation указывает в кеш-каталоги установщиков — «сиротами» их считать нельзя, и удалять нельзя. Улучшение: в инвентаризации/`unused-detect` исключать пути `Package Cache\` из дельты (отдельный осторожный трек «кеши Package Cache» можно считать особым типом, но не по LocExists).

## Прочие замечания

(заполняется по ходу прогона)

### Z1. `C:\Windows\392667600.dat` — «неизвестное» из скилла, встретилось вживую
Файл 128 МБ в корне `C:\Windows`, создан 2026-08-18 19:20 (за ~15 мин до Фазы 0), **модифицировался в 19:46 — прямо во время наших сканов**. Без версии/подписи/описания, заголовок бинарный. Похоже на активный системный временный файл (Windows Update/Defender/MRT). Решение по скиллу: НЕ удаляем, показать пользователю, спросить. Отличный живой кейс для Фазы 3/6.

### Z2. Сканы и реестр программ — здоровые сигналы
- `scan.ps1` single-pass за 296 с на C:\ (148 ГБ), топ-файлы/папки/дубли читабельны; системные дубли корректно ушли в `dupes_system.txt` (WinSxS/DriverStore/lxss/assembly).
- `installed.csv` 252 записи, 12 с `LocExists=False` — но все они Package Cache (см. U6), настоящих сирот-кандидатов нет.
- Большинство крупных программ стоят на D: (LoL 38,6 ГБ, Vortex, STM32CubeMX, Arduino...) — на C: «жирных» кандидатов почти нет.

### Z3. Нюанс именования: функция `H` конфликтует с алиасом `h` → `Get-History`
В тестовых скриптах функция с именем `H` молча вызвала `Get-History` (алиасы имеют приоритет над функциями). Косвенно подтверждает питфолл скилла «любые имена-ключевые слова/коллизии алиасов». Стоит упомянуть в Pitfalls: избегать однобуквенных имён, пересекающихся с алиасами PS.

### Z4. Свободное место «не выросло» несмотря на удаление 1,2 ГБ
По ledger удалено ~1,18 ГБ (installers 129,8 МБ + leftovers 1077,6 МБ), но Get-Volume C: показывает ~55,35 ГБ — практически baseline (55,37). Значит, за ~25 мин параллельного фона система потребила ~1,2 ГБ (кандидаты: активно писавший `392667600.dat`, Windows Update/Defender/MRT, pagefile). Для честной Фазы 10: дельта тома не равна сумме `removed_mb`, и отчёт обязан это проговорить, а не делать вид «освободилось N = разница томов». Хороший живой кейс для формулировки итога.

### Z5. `scan.ps1` переоценка Office-кеша
В Фазе 3 я оценил C1 «~0,3 ГБ» по дублям (2×MSORES.DLL + 2×EXCEL.EXE), а фактически папка `Updates\Download` — 946,5 МБ. Пояснение: в отчёте по дублям видны только парные файлы, полный объём кеша заметно больше. Учебное: размер «дубль-пары» ≠ размер каталога-источника.
